# Логика обеспечения математической точности в MathForge

## Краткая идея

В проекте MathForge математическая точность обеспечивается не языковой моделью, а детерминированным символьным ядром на базе SymPy. LLM-компоненты используются только для вспомогательных задач: извлечения текста из изображения, генерации подсказки естественным языком или подготовки черновиков шаблонов. Решение, проверка эквивалентности и вычисление правильных ответов выполняются кодом backend.

Главный принцип архитектуры:

> LLM может объяснять и извлекать данные, но не является источником математической истины.

## 1. Генерация задач через SymPy

Основная генерация задач реализована в `backend/app/core/engine/generator.py` в классе `TaskGenerator`.

Шаблон задачи хранится как структурированный JSON:

- `sympy_expr` - выражение в синтаксисе SymPy;
- `ranges` - диапазоны случайных коэффициентов;
- `constraints` - ограничения на коэффициенты;
- `texts` или `question_text` - локализованный текст условия;
- `equation_rhs` - правая часть уравнения, если задача требует решения уравнения.

При генерации система:

1. Берет математический шаблон из базы.
2. Случайно выбирает коэффициенты из разрешенных диапазонов.
3. Проверяет ограничения на коэффициенты.
4. Подставляет коэффициенты в SymPy-выражение.
5. Для уравнений вызывает `sp.solve(...)`.
6. Для вычислительных задач вызывает `sp.simplify(...)`.
7. Возвращает условие и ответ в LaTeX через `sp.latex(...)`.

Это снижает риск ошибок, потому что ответ не пишется вручную и не генерируется LLM. Он получается из одного и того же формального выражения, которое задает условие задачи.

## 2. Проверка пошагового решения

Проверка шагов ученика реализована в `backend/app/core/engine/arbitrator.py` в классе `Arbitrator`.

Логика проверки:

1. Решение ученика представляется списком шагов.
2. Каждый шаг парсится в SymPy-выражение.
3. Если шаг является уравнением, например `2*x + 4 = 10`, он приводится к форме `lhs - rhs`.
4. Для каждой пары соседних шагов вычисляется:

```text
simplify(expr_current - expr_next)
```

5. Если результат равен `0`, переход считается математически корректным.
6. Если результат не равен `0`, система фиксирует первый ошибочный шаг.
7. Дополнительно проверяется мультипликативная эквивалентность уравнений, например переход `2x = 6 -> x = 3`.

Таким образом, система проверяет не финальный ответ как строку, а математическую эквивалентность соседних преобразований.

## 3. OCR и рукописные решения

Для фотографий решений используется pipeline в `backend/app/api/routes/ocr.py` и `backend/app/core/engine/vision_agent.py`.

Важно: Vision-модель не решает задачу. Она только извлекает строки шагов из изображения.

Pipeline:

1. Backend проверяет тип файла: JPEG, PNG или WebP.
2. Backend проверяет размер файла.
3. VisionAgent отправляет изображение модели с инструкцией вернуть только JSON-массив строк.
4. Ответ модели парсится и валидируется как список шагов.
5. Извлеченные шаги передаются в `Arbitrator`.
6. Математическая проверка выполняется SymPy.

За счет этого OCR может ошибиться при распознавании текста, но сама математическая валидация не делегируется LLM.

## 4. Подсказки от ИИ не являются источником проверки

Подсказки генерируются в `backend/app/core/engine/llm_agent.py`.

LLM получает:

- последний корректный шаг;
- шаг, где появилась ошибка;
- язык пользователя.

LLM не получает роль математического валидатора. В системной инструкции явно указано, что модель не должна решать уравнение и не должна продолжать вычисления. Ее задача - объяснить правило, которое могло быть нарушено.

То есть порядок такой:

1. SymPy находит ошибочный переход.
2. LLM объясняет ошибку человеку.

Не наоборот.

## 5. Защита от плохих шаблонов

Шаблоны задач могут поступать из разных источников: seed-данные, база данных, извлечение из PDF. Поэтому проект содержит несколько уровней защиты.

### Проверка при генерации

Если шаблон содержит некорректный `sympy_expr`, генератор выбрасывает ошибку, а route пропускает такой шаблон и пробует другой. В `backend/app/api/routes/tasks.py` для генерации задач добавлен таймаут на один шаблон, чтобы проблемное SymPy-выражение не зависило весь запрос.

### Проверка RAG-шаблонов

В `backend/app/services/rag_parser.py` LLM может извлечь шаблон из PDF, но перед сохранением шаблон проходит структурную проверку и SymPy-валидацию. Код требует:

- валидный JSON;
- наличие обязательных полей;
- SymPy-совместимый `sympy_expr`;
- реалистичные диапазоны коэффициентов;
- отсутствие Unicode-математических символов в `sympy_expr`.

Это означает, что LLM может предложить шаблон, но математическое ядро должно подтвердить, что выражение пригодно для генерации.

## 6. ORT-генератор

Отдельный генератор ORT находится в `backend/app/services/ort_generator.py`.

Он также использует SymPy:

- выражения парсятся через `sp.sympify(...)`;
- коэффициенты подставляются в выражения;
- сравнение колонок выполняется через `sp.simplify(val_A - val_B)`;
- правильный вариант ответа вычисляется программно;
- неправильные варианты генерируются вокруг правильного ответа.

Это защищает тестовые задания от LLM-галлюцинаций: варианты ответов строятся от вычисленного SymPy-значения.

## 7. Роль базы данных

База данных хранит не просто текст задач, а параметризованные математические шаблоны. Это важно для точности:

- условие и ответ связаны одним `sympy_expr`;
- коэффициенты выбираются из контролируемых диапазонов;
- ограничения предотвращают нежелательные случаи, например отрицательный дискриминант там, где нужны действительные корни;
- активность шаблонов можно отключать, если шаблон оказался плохим.

## 8. Что именно гарантируется

Проект гарантирует:

- правильность вычисленного ответа для корректного SymPy-шаблона;
- проверку эквивалентности шагов через символьное упрощение;
- отсутствие LLM в роли финального математического судьи;
- детерминированную проверку ошибок в ручном и OCR-вводе;
- фильтрацию или пропуск невалидных шаблонов;
- генерацию LaTeX-ответов из SymPy, а не из свободного текста.

## 9. Ограничения

Точность не является абсолютной во всех математических областях. Есть ограничения:

- если OCR неправильно распознал шаг, SymPy будет проверять уже ошибочно извлеченный текст;
- если пользователь пишет выражение в формате, который парсер не понимает, появится parse error;
- SymPy хорошо покрывает алгебру, арифметику, базовый анализ и матрицы, но не является полноценным proof assistant;
- проверка `simplify(expr_a - expr_b) == 0` надежна для многих школьных и университетских преобразований, но не доказывает все возможные тождества во всех областях;
- LLM-подсказка может быть педагогически неточной, но она не влияет на решение о корректности;
- качество генерации зависит от качества `template_json`.

## 10. Вывод для диплома

MathForge использует гибридную архитектуру: LLM отвечает за интерфейсные и языковые задачи, а математическая истинность контролируется символьным движком SymPy. Такая архитектура уменьшает риск галлюцинаций, потому что генерация ответов, проверка шагов и сравнение выражений выполняются формальными алгоритмами.

Ключевая гарантия точности состоит в разделении ответственности:

- SymPy - вычисляет, упрощает, решает и проверяет;
- LLM - распознает, объясняет и помогает пользователю;
- backend - валидирует входные данные, управляет шаблонами и не допускает, чтобы LLM становилась источником математического ответа.
